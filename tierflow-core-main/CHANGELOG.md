# Changelog

本文件记录 TierFlow（new-api fork）各版本的主要改动。遵循语义化版本，最新在上。

## v3.2.3

本版以修复为主。核心是 DeepSeek 思考模式的 `reasoning_content` 回传从「全局选项驱动」改为
「渠道类型内建」—— 旧选项默认为空，等于这条兜底从未跑过；同批修掉一条会跨用户串号的缓存
安全问题。另有三类**静默数据损坏**：不报错、不留痕，只在事后对账时才显形。

### 新增
- **兑换码支持开通订阅套餐**：同一个兑换框通吃额度码与订阅码，不新增页面、不新增接口，后端按 `type` 分派。所有校验都在 `Status→Used` 跃迁之前完成，任何拒绝都让整个事务回滚、兑换码保持可用——否则一次因套餐停用而失败的兑换会白白烧掉用户的码。订阅分支复用 `CreateUserSubscriptionFromPlanTx`，沿用与余额购买相同的购买守卫，并写 money=0 的订单 + 账单镜像（不写的话兑换来的订阅在账单页完全不可见）。
- **模型列表改用连续展示序号**：`models` 表软删除、主键不回收，列表上会跳号（1、2、5、9…）。ID 列改展示后端下发的 `display_id`，真实 `id` 仍随数据返回，编辑/删除/批量操作全部依赖它。

### 破坏性变更
- **`POST /api/user/self/topup` 的 `data` 字段由数字变为对象**。此前返回充值到账的额度数字（`{"data": 500}`），现返回 `RedeemResult`：`{"data": {"type": 0, "quota": 500, "plan_title": "", "end_time": 0, "sub_id": 0, "token_key": ""}}` —— 额度码只填 `quota`，订阅码填 `plan_title`/`end_time`/`sub_id`/`token_key`。仓内前端已同步；**外部脚本或自建前端若把 `data` 当数字读，会静默拿到一个对象**（不会报错，只会算出 `NaN` 或显示 `[object Object]`），需要改读 `data.quota`。

### 修复
- **DeepSeek 思考模式的 reasoning_content 回传改为渠道类型内建，零配置生效**：DeepSeek 上游要求「两条 user 消息之间若发生过工具调用，该段 assistant 的 `reasoning_content` 必须回传」，否则 400 `The reasoning_content in the thinking mode must be passed back to the API.`；客户端（WorkBuddy / Codex 等）重建历史时会剥掉这个非 OpenAI 标准字段。这是上游协议要求而非站点偏好，因此改为**渠道类型选了 DeepSeek(43) 就自动处理**，判定见 `service.NeedsReasoningContinuity(channelType, modelName)`。
  - **删除系统选项 `ReasoningContinuityModels`**（含管理端「需 reasoning 连续性的模型」整节 UI 与两条 i18n 文案）。该选项默认为空 ⇒ `IsReasoningContinuityModel` 直接返回 false ⇒ 整条链路是死代码，每个部署都要先踩一次上游 400 才会有人去开它。DB 里的历史行会成为无人读取的孤儿记录，可自行删除，留着无副作用。
  - **缓存按「用户 + 上游模型」分域**（安全）：reasoning 缓存 key 此前只哈希 assistant 消息内容与 `tool_calls`，而命名空间是进程级的、开 Redis 后还跨实例共享 —— 两个用户发出内容相同的 assistant 消息（短回复如「好的。」极易撞）就会共用一条缓存，A 的私有思考链会被当作 B 的历史草稿注入 B 发往上游的请求。旧实现因选项默认为空而从未生效，这次零配置生效会把它变成活的，故一并修掉。
  - **处理范围**：完全没有工具调用的纯对话历史一条都不碰；同渠道下的非思考模型（`deepseek-chat` / `deepseek-reasoner`）与 `-none` 后缀显式关闭思考的请求也不注入。一旦历史里出现过工具调用，则整段对话的 assistant 全部补齐 —— 曾按 user 消息切段实现，但那会让「先纯聊两句、再调工具」这种常见形状里靠前的 assistant 丢掉 `reasoning_content`；文档只说那些轮次「不需要」而非「不能带」，且上游是否真按段校验从未测出来。风险不对称：漏补是硬 400，多补则已实测被上游接受。
  - **空 `tool_calls` 数组归一**：`[]` 与「无 `tool_calls`」此前产生不同摘要（`"[]"` vs `""`），而响应侧写缓存传 nil、客户端回传时常序列化成显式 `[]` —— 两侧 key 对不上，真实草稿命中不了、静默退化成占位。同理，跳过判定改用 `ParseToolCalls()`，避免给「既无内容也无工具调用」的 assistant 注入 `reasoning_content` 造出一条三无消息。
  - **响应侧缓存同步改为按渠道类型判定**：deepseek adaptor 的 `DoResponse` 委托给 openai adaptor，所以 reasoning 缓存写入的代码物理上在 `relay/channel/openai` 包里，但归属的渠道类型仍是 DeepSeek —— 判定要跟着渠道走而不是跟着包走。
  - **已知不覆盖**：把 DeepSeek 配成 `ChannelTypeOpenAI`(type=1) 的场景（如指向聚合商的兼容渠道）不做处理，聚合商无法从渠道类型上识别。`relay/channel/openai` 下有一条反向用例把这个取舍钉死，避免日后被"顺手"加回去波及非 DeepSeek 上游。要覆盖需把渠道改成 DeepSeek 类型。
  - **验证边界**：「旧选项默认为空导致整条链路是死代码」与「占位 `(omitted)` 能被上游接受」两件事均已实测确认（注入后 prompt_tokens 372→378 / 365→373，请求 200）。但触发本次排查的那条客户端 400 **未能复现** —— 关闭处理后，AIPING 四种消息形状（单段工具调用 / 两轮 user / 流式 / 多轮工具调用）与官方 `api.deepseek.com` 直连，共 5 组全部返回 200。因此本条按「对齐上游文档的加固」记，而非对该次故障的确认性修复。
- **兑换额度给已软删除的账号会「兑换成功、零到账、码被烧掉」**：`Redeem` 的额度分支只判 `err`、不判 `RowsAffected`。`User` 带 `gorm.DeletedAt`，GORM 会给那条 `UPDATE users SET quota = quota + ?` 自动追加 `deleted_at IS NULL` —— 账号在鉴权之后被软删除时影响 0 行且 `err == nil`，事务一路走到把兑换码置为 `Used`。用户看到「兑换成功」和面额、额度一分没到、码被永久消耗，而本次同批加入的状态回退守卫又禁止管理员把 `Used` 改回 `Enabled`，完全无从补救。现在 0 行即返回 `ErrRedemptionUserMissing` 让整个事务回滚，兑换码保持可用。余额购买套餐与升级补差价那两条扣款路径不受影响：它们扣款前先 `lockForUpdate().First(&user)`，软删除用户会在那里就 `ErrRecordNotFound` 回滚。
- **兑换码开通的订阅被计进「付费充值笔数」**：这类订单金额记 0 但仍写 `TopUp` 行（不写的话该订阅在 `/billing` 与管理端订单列表完全不可见），而 `GetFinanceSeries` 的充值聚合 `COUNT(*)` 了区间内所有成功 `TopUp`，且把非 `balance` 的 `payment_method` 一律当现金 —— `redemption` 恰好满足。¥ 汇总不受影响（金额为 0），但发一批促销码就会让看板显示「N 笔付费充值」对 ¥0 收入，由 `Recharge ÷ RechargeCount` 推出的客单价也被压向 0。现在在 `WHERE` 里整条剔除：它既不是现金也不是余额购买，不属于充值口径。
- **只改名的 `PUT /api/redemption/` 会把订阅码静默改写成 ¥0 额度码**：请求体绑定到零值结构体，「没写的字段」与「显式写了零值」不可区分，而 `Redemption.Update()` 的 `Select` 白名单会把零值一并强写入库。于是一个 `{id, name}` 的 PUT 会把 `type`/`plan_id`/`quota`/`expired_time` 一起清零 —— `type` 归 0 被 `validateRedemptionTypeAndPlan` 当成合法的额度码放行、`plan_id` 被强制清零，管理端从此显示「额度码 ¥0.00」，兑换它的用户既拿不到订阅也拿不到余额，而码照样被消耗。改为两段式绑定：先只取 `id` 定位记录，再把现有记录作为种子二次绑定（`ShouldBindBodyWith` 缓存请求体，可重复绑定），省略的字段保持原值，写了的字段才覆盖。同一处修复顺带堵住了「省略 `name` 会把名字清空」「`status_only` 模式下省略 `status` 会把状态写成 0」这两个同源问题。
- **已兑换的兑换码可被管理员改回可用**（既有缺陷，非本次引入）：`PUT /api/redemption/?status_only=1` 此前不校验当前状态，把 `Used` 改回 `Enabled` 后该码可再次兑换 —— `UsedUserId`/`RedeemedTime` 被覆盖、首次兑换的台账被静默抹掉，订阅码还会再开一份订阅并再签发一把 Key。前端行操作里的 `canToggle` 只是 UI 门，直接 PUT 就能绕过。现在后端一并拒绝内容修改与状态回退。撤销已发放的订阅请走「作废用户订阅」。
- **模型表的绑定渠道顺序每次刷新都在变**：两条路径都没有定序 —— 规则模型（前缀/后缀/包含匹配）把渠道收进 `map[int]BoundChannel` 后直接 `range` 出来，Go 的 map 迭代顺序是随机的；精确模型走的 `GetBoundChannelsByModelsMap` 是一条不带 `ORDER BY` 的 `SELECT DISTINCT`，SQL 层同样没有顺序保证。而本批改动把 `bound_channels` 从默认隐藏改成了默认显示，于是管理员每次刷新/翻页看到的渠道徽章排列都不同，没法靠肉眼比对某个模型的上游绑定有没有变。现在规则路径按渠道 id `sort.Slice`（与既有的 `sort.Ints(QuotaTypes)` 同源处理），SQL 路径补 `ORDER BY channels.id`。
- **同名渠道的徽章在视觉上完全无法区分**：后端改为按渠道 id 去重后会如实吐出每一条渠道，但前端徽章只渲染 `c.name`、配色也只按 `c.name` 取 —— 两条同名渠道（不同 id、可能不同类型与 base_url）显示成两个一模一样的徽章，恰好抵消了后端不合并的意义。现在仅对**本行内重名**的渠道追加 `#id` 并把配色键也带上 id，其余保持原样，不给常见情况增加噪音。
- **`BoundChannel` 缺少渠道 id**：`enrichModels` 原按「名称+类型」去重，同名同类型的两个渠道会被静默合并成一个徽章。改为按渠道 id 去重。
- **兑换失败的具体原因不再被折叠**：此前事务内所有失败都收敛成 `ErrRedeemFailed`，用户永远只看到「兑换失败，请稍后重试」，i18n 里那批具体译文零使用点。现按哨兵错误分派，并区分「已被兑换」与「被管理员禁用」。
- **兑换码订单拒绝自动退款**：这类订单无资金可退且码不会返还，`AdminRefundSubscriptionOrder` 现直接拒绝并引导改用「作废用户订阅」，与余额订单金额未知时的处置同源。

## v3.2.2

给 v3.2.1 的对话消息记录补上管理端开关 —— 此前它默认关闭且**没有任何开启入口**,
一个开不起来的功能实际等于没有。顺带订正 v3.2.1 条目里的两处事实错误。

### 新增
- **运营设置 → 对话消息记录**(`/system-settings/operations/message-capture`):9 项全部可视化配置 —— 总开关、存储目录、排除用户 ID、每日条数上限、历史重放上限、单条正文上限、请求体上限、响应缓冲上限、异步队列容量。
- **后端零改动**:`ExportAllConfigs()` 启动时已把 `message_capture_setting.*` 灌进 `OptionMap` 并由 `GetOptions` 下发(这 9 个 key 都不命中 Token/Secret/Key 敏感后缀过滤),`UpdateOption` → `updateOptionMap` 也已把 `a.b` 形态的 key 泛型路由到注册的 config 结构体。读写两条路本来就通,缺的只是前端。
- 字段说明写清三件容易踩的运行时事实:**开关即时生效不需重启**(中间件每请求解引用配置指针,写协程在启动时已无条件拉起);**`queue_size` 需重启**(`msgChOnce` 只在启动时创建一次通道);**`dir` 只对新打开的文件生效**(已打开的句柄会继续追加旧路径,直到跨天或出错被回收)。开关打开时额外提示消息内容以明文落盘,需确认隐私政策已覆盖、存储目录已做备份与访问控制。

### 修复
- **v3.2.1 条目里的管道计数端点写错了**:实际是 `GET /api/status/test`(管理员)下的 `http_stats.message_capture`,不是 `/api/status`。已订正。
- **v3.2.1 的「暂无开关 UI」限制描述不准确**:并非只能改库加重启 —— 通过通用设置接口 `PUT /api/option/` 一直就能即时开关,只是没有 UI 入口。已订正。

### 其它
- 表单实现有两处会**静默出错**、值得记一笔:其一,react-hook-form 7 把带点的 `name` 当嵌套路径,zod schema 若直接用扁平字面 key(`'a.b'`),表单状态会与校验结构错开,`handleSubmit` 静默不调用 `onSubmit`——保存按钮看着毫无反应,既无 toast 也无报错;沿用 `performance-section.tsx` 的做法,内部用嵌套对象建模、落库前才拍平。其二,`getOptionValue` 只保留 `defaults` 里存在的 key,并按 `typeof 默认值` 决定如何解析接口返回的字符串,因此前端默认值必须与 Go 侧逐一对齐——漏一个 key 等于该项永远读不到,boolean 误写成 string 则开关会从字符串 `"false"`(truthy)渲染、读起来永远是开。
- 验证方式:除 typecheck / lint 基线比对外,另起真实后端做完整往返 —— `GET /api/option/` 读到 9 个 key 且值与 Go 默认逐一相符,按前端实际发送的 JSON 类型 `PUT` 后回读全部匹配,重启后仍匹配。这条才是能证明类型转换层正确的检查。

## v3.2.1

新增用户对话消息记录管道(**默认关闭**,不开启则对现有链路零影响,故按补丁版发布),
并修复该管道在代码审查中暴露的一批静默丢数据缺陷;顺带修掉渠道/模型等管理页
删除确认弹窗显示英文的问题。

### 新增
- **用户对话消息记录**(`message_capture_setting.enabled`,默认 `false`):把经过网关的对话内容按 `uid/日期` 落成 JSONL,用于用户画像分析。热路径只做三件事 —— 端点判定、tee 响应字节、请求结束时拷请求体并**非阻塞**投递;解析 JSON / 算哈希 / 查 Redis / 写磁盘全部在异步管道里,任何失败只计数不回压到用户请求。图片与音频只计数不留内容;推理过程单独存 `reasoning` 字段,不混进正文。
- **会话识别靠链式前缀哈希**:API 请求里没有 `conversation_id`,但第 N+1 次请求的消息前缀恰好等于第 N 次的全部消息加回复 —— 用这个前缀关系把多次请求串成会话。游标存 Redis,无 Redis 时降级到进程内。
- **对外用户标识 uid**(`model/user_uid.go`):12 位纯数字,`crypto/rand` 生成。落盘数据属于对外资产,用内部自增 id 会让它重新变成可枚举值。
- **`GET /api/status/test`(管理员)暴露管道计数**,位于 `http_stats.message_capture` 下:`dropped_queue_full` / `dropped_no_quota` / `dropped_parse` / `dropped_no_uid` / `dropped_req_too_large` / `resp_truncated` / `write_errors` / `records_written`。静默丢弃是最坏的失败模式 —— 事后看数据只会觉得"这个用户不活跃"。
- **优雅退出**:`main.go` 的 `server.Run` 换成 `http.Server` + SIGINT/SIGTERM 处理,先 `srv.Shutdown` 再 `StopMessageStore(5s)`。此前进程收到 SIGTERM 直接被杀,队列中和 bufio 缓冲里的数据全部丢弃。

### 修复
- **写失败会让用户当天的文件永久写不进**:`bufio.Writer` 的错误是**粘滞**的 —— 首次失败后 `b.err` 被记住,之后每次 `Write`/`Flush` 都直接返回同一个错误、根本不会碰到 OS。一次瞬时 ENOSPC 就足以让该用户当天再无一条记录落盘,且只能靠重启恢复。现改为任何写失败都丢弃句柄,下次写入自动重新打开(`O_APPEND`,已有内容不受影响)。
- **文件句柄跨天泄漏**:句柄按 `uid+日期` 缓存,跨天后旧 key 再也不会被写到却从不关闭 —— 每个活跃用户每天泄漏一个 fd 且永不回落,最终打爆 `RLIMIT_NOFILE`,连带拖垮上游连接与数据库句柄。现由 `flushAll` 回收非当天句柄,并加 `maxOpenFiles=256` + LRU 兜底突发。
- **历史最长的用户一条都记不下**:游标未命中时整段历史被当作新消息重放,`len(pending)` 可能直接超过 `QuotaPerDay`,于是该用户**永远**通不过配额判定 —— 恰好把最值得画像的重度用户静默排除在数据之外。现重放段裁到 `MaxReplayMessages`(新配置,默认 50)并再压到 `QuotaPerDay-1`,被丢弃的前缀在索引上标 `truncated`。
- **纯思考回复会打断会话链**:推理模型常常 `content` 为空、内容全在 `reasoning_content` 里,而请求侧解析器会跳过这种消息 —— 把它算进链哈希,下一轮就永远对不上,于是每轮都当新会话重放整段历史。现按请求侧解析器的跳过条件过滤后再入链。
- **相同开头的两段会话被并成一个**:链游标被消费后不作废,另一段开头相同的会话会捡走它。现在游标前移后即作废。残留歧义(B 的第二轮赶在 A 前移之前到达)已写入代码注释 —— 从请求字节里区分不出来,要根治需客户端传入会话标识。
- **请求体被截断成非法 JSON**:请求体上限此前复用 `MaxTeeBytes`(那是按 SSE 响应膨胀倍率估的值),超过 2MB 的长历史请求会被从中间截断,解析必然失败;而请求体只增不减,之后每一轮都丢。现独立成 `MaxReqBodyBytes`(新配置,默认 10MB),超限整条跳过并计入 `dropped_req_too_large`,不再把半截 JSON 喂给解析器。
- **流被中断却记成完整回复**:SSE 响应头一 flush 出去,HTTP 状态就永远是 200,上游掉线无从判断,半句话会被当成模型的完整输出。现按终止标记(OpenAI `[DONE]` / Claude `message_stop`)判定,缺失即标 `truncated`。刻意不用 `finish_reason` —— 它可能先到、流随后被切。
- **Redis 配额上限会失效**:`Get` 失败(读超时等)与 key 不存在无法区分,一律当 0 处理,配额上限形同虚设;多节点共用一个 Redis 时读写之间本身也有竞态。现改为原子 `IncrBy`、超限再 `DecrBy` 退回,`Expire` 提到判定之前,避免被拒的那次留下无 TTL 的永久 key。
- **单条写失败会造出半截数据**:配额按整轮原子扣除,但写入循环遇错即 `return` —— 正好产生"有提问没回复"的半截记录,而这恰是原子判定要避免的。现改为继续写完剩余记录、推进游标,并把该轮标记为 `truncated`。
- **渠道/模型等管理页删除确认弹窗显示英文**:这些文案要么是硬编码模板字符串完全没走 `t()`,要么被拆成几个词的碎片 key —— 后者切到中文会得到「您确定要删除吗 5 渠道？」这种语序错乱的句子。涉及渠道/模型行内删除、删除所有已禁用渠道、按标签批量改优先级/权重、重置 Passkey / 重置 2FA、供应商 / 模型组 / 路由配置 / 预填分组删除等 11 个文件,改为整句 key + 插值。
- **订阅胶囊文案重复**:套餐名后不再追加「订阅」后缀 —— 正式环境的套餐名本身就带该二字,拼接会显示成「Pro 订阅 订阅」。

### 其它
- 新增 10 个针对性 Go 用例(句柄恢复 / 跨天回收 / 句柄上限 / `closeAll` 落盘 / 配额无残留 / 游标作废 / `chainVisible` / 长历史保尾 / 流中断标记 / 超大请求体计数)。
- 修掉原有两个 capture 测试里潜伏的竞态:`http.Post` 返回时中间件的 post-`Next()` 段可能还没跑完,统一改为先 `gw.Close()`(阻塞到在途请求结束)再排空管道。
- `.gitignore` 的 `messages/` 加锚点为 `/messages/`,避免误伤任意层级下同名目录。

### 已知限制
- **多实例不能共享同一份存储**:文件名不带节点标识,多进程 `O_APPEND` 写同一文件会让行交错撕裂。当前单节点部署安全,若改用 NFS/EFS 共享存储必须重新引入节点维度,或改由单一实例负责落盘。
- **`/v1/responses`、`/v1/completions` 与 Gemini 端点没有原生请求解析器**,会按 OpenAI 结构尝试并大概率失败、计入 `dropped_parse`。功能默认关闭故不影响现状,开启后这几个端点的数据是缺的。
- **暂无开关 UI**:只能通过通用设置接口 `PUT /api/option/` 以 key `message_capture_setting.enabled` 开关(即时生效,无需重启);直接改 `options` 表则需重启才会加载。管理端 UI 见 v3.2.2。

- 删组引用检查的裸 SQL 列名错误：GORM 把 `Tier1Model` 映射为 `tier1_model`（`tier_1_model` 是 json tag），e2e 实测暴露后更正。
